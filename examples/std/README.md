# Host-примеры: CSP storage и каркас ПН

Две отдельные программы без платы, SPI и Flash:

- `storage_sender` бесконечно отправляет нумерованные текстовые сообщения раз в секунду;
- `storage_receiver` бесконечно принимает CSP datagram и сохраняет payload в `RamStorage`.

Обе программы запускаются без аргументов и работают до ручной остановки (`Ctrl+C`).
У приёмника нет ограничения по числу сообщений и нет idle timeout.

## Запуск

Все команды выполнять из корня workspace. В первом терминале:

```sh
cargo run -p examples-std --bin storage_receiver --locked
```

Во втором терминале:

```sh
cargo run -p examples-std --bin storage_sender --locked
```

Отправитель сразу начинает передавать `packet #1: temperature=23.5`,
`packet #2: temperature=23.5` и так далее. Приёмник печатает источник, payload
и число сохранённых записей. Если отправитель ещё не запущен, приёмник просто ждёт.
После остановки/повторного запуска отправителя приёмник продолжает работать.
Нумерация отправителя при перезапуске начинается заново.

Настройки находятся в `src/storage_demo.rs`: UDP-адреса, CSP-узлы и порты,
период отправки, размер записи и ёмкость очереди. CLI-параметров нет.

## Интерфейсы

Прикладной код работает через `sat_core::net::DatagramSocket`:

1. `CspDatagramSocket` из `src/csp_demo.rs` оборачивает `sat_csp::Socket`.
2. `sat_csp::Runner` кодирует/декодирует CSP-кадры и фильтрует адреса и порты.
3. `UdpCspInterface` из `src/mock/phy.rs` реализует `sat_csp::CspInterface`:
   один UDP datagram переносит один полный CSP-кадр.

Каждая программа одновременно выполняет свой Runner и прикладной цикл.
Это настоящий CSP поверх UDP, не передача текста напрямую через carrier.
Старый `PhyLayer` не используется и не восстанавливается.

Адреса этого примера:

- отправитель: UDP `127.0.0.1:25041`, CSP node `1`, source port `10`;
- приёмник: UDP `127.0.0.1:25042`, CSP node `2`, destination port `11`.

Один экземпляр каждого бинарника занимает соответствующий UDP-порт.
CSP-адреса и порты независимы от UDP-адресов.

`receive_and_store<D: DatagramSocket, S: Storage>` принимает полное сообщение,
сохраняет только payload и возвращает `DatagramMetadata` с источником и длиной.
CSP-заголовок и метаданные источника в FIFO не записываются.
Номер пакета — часть демонстрационного текста, не отдельный сетевой протокол.
Это отдельный host-пример, не миграция подсистем или основной firmware.

## Ёмкость и ошибки

- RAM FIFO содержит до 16 записей, каждая не более 256 байт.
- Host CSP MTU равен 262 байтам: заголовок 6 байт и payload до 256 байт.
  Это настройка UDP-демо, не ограничение реального LoRa-радио. При MTU 255
  максимальный payload был бы 249 байт.
- После заполнения приёмник **не завершается**: продолжает получать пакеты,
  печатает `Full` и отклоняет новые записи. Старые не перезаписываются.
- Автоматического `pop`/`clear` нет. Без отдельного потребителя очередь остаётся
  полной. Перезапуск приёмника создаёт пустую очередь и теряет прежние записи.
- Payload длиннее 256 байт отклоняется CSP-сокетом отправителя до передачи.
  Если передать helper хранилище с меньшим лимитом, oversized payload отклоняется
  хранилищем; следующий datagram продолжает приниматься.
- Если прикладной выходной буфер слишком мал, `CspDatagramSocket` возвращает ошибку,
  сохраняет полное сообщение и позволяет повторить приём с большим буфером.
- UDP-carrier сначала принимает полный datagram во внутренний буфер. Кадр,
  превышающий буфер Runner, отклоняется без частичного копирования и отбрасывается.
  Невалидные CSP-кадры, другие узлы и непривязанные порты до хранилища не доходят.
- Ошибки Runner логируются; через 250 мс его цикл запускается снова. Потерянный
  при ошибке отправки кадр автоматически не повторяется. Ошибка первоначального
  bind, например занятый порт, не позволяет запустить соответствующую программу.
- Используются CSP datagram, не RDP: нет ACK/retry/deduplication. `queued`
  у отправителя означает только принятие в локальную очередь CSP;
  фактическое сохранение видно по `stored` приёмника.
- RAM не является файлом или persistent Flash. При остановке приёмника записи теряются.

## Проверки

```sh
cargo test -p examples-std --lib storage_demo --locked
cargo test -p examples-std --lib mock::phy --locked
cargo test -p examples-std --lib --locked
cargo build -p examples-std --bin storage_sender --bin storage_receiver --locked
cargo test -p sat-drivers --test ram_storage_consumer --locked
```

Storage-тесты используют настоящий CSP Runner поверх loopback UDP на временных
портах. Проверяются FIFO, бинарные/пустые payload, источник, фильтрация узлов/портов,
отсутствие overwrite, продолжение после переполнения и oversized записи,
сохранение сообщения при малом выходном буфере и максимальный payload 256 байт.
Сетевые ожидания этих тестов ограничены deadline.

Бинарник `sat` и тест `cdh_system` включаются только через
`--features subsystems`. Тест использует текущие интерфейсы CDH и транспорта;
`src/bin/sat/main.rs` остаётся незавершённым. Storage-демо не требует этой feature.

## ПН: отдельные TX и RX через CSP/UDP

Feature `payload` включает targets `payload_tx`, `payload_rx` и `payload_commands`,
но не включает `sat` и `cdh_system`. Features `payload` и `subsystems` — пустые
маркеры для `required-features`; зависимости `sat_subsystems`, `sat_drivers`
и `embassy-sync` обязательны. Для `sat_subsystems` отключены default features
и включён только `log`, без одновременного выбора `defmt`.

В первом терминале, из корня workspace:

```sh
cargo run -p examples-std --bin payload_rx --features payload --locked --offline
```

Во втором:

```sh
cargo run -p examples-std --bin payload_tx --features payload --locked --offline
```

Обе программы запускаются без аргументов и работают до `Ctrl+C`.
TX использует один UDP-carrier `127.0.0.1:25051` и CSP endpoint `2:20`.
У RX один АСП CSP/UDP-carrier `127.0.0.1:25052`, CSP node `1` и порты
`10` (маяки АСП), `11` (данные АСП), `20` (внешний тестовый bridge, endpoint `1:20`).
Он направляет UDP-кадры на тестовый TX `127.0.0.1:25051`; используются один Runner,
один набор ресурсов и одна очередь отправки. Это имитация линии АСП 868 МГц,
а не настройка реальной частоты: UDP-carrier не моделирует радио.
НС и линия 435 МГц относятся к отдельной подсистеме БКУ, не к `payload`.
TX привязывает только командный порт `20`, поэтому маяки не декодирует и не выводит.
Порты не пересекаются со storage-демо.
UDP-адреса и CSP-узлы/командный порт заданы в `src/payload_demo.rs`, конфигурация
маяков подключена в `src/bin/payload_rx.rs`.

TX по-прежнему отправляет только `Ping`: данные АСП он не генерирует, отдельный
процесс АСП для этого примера не добавлен. TX отправляет `Ping` с номером запроса
и ждёт подтверждения до двух секунд.
После ответа или timeout ждёт одну секунду и отправляет следующий запрос с новым
номером. Ответы с другим номером или CSP-источником игнорируются и не продлевают
исходный deadline.

На RX одновременно работают один CSP Runner, внешний тестовый bridge
`serve_commands` и настоящий `PayloadSystem`. Bridge — standalone-адаптер к каналам
команд и событий, не часть runtime ПН и не обработчик прямых команд НС:

1. Bridge принимает корректный запрос через `DatagramSocket` от endpoint `2:20`.
2. Передаёт `PayloadCommand::Ping` в канал подсистемы.
3. Ждёт `PayloadEvent::Pong`, то есть выполнения обработчика `Ping`.
4. Только после этого отправляет `Executed` с исходным номером запроса.

RX печатает `Ping executed (Pong); confirmation queued`, TX —
`execution confirmed by RX`. Это не подтверждение одного лишь получения пакета.
Пример проверяет реальный обмен CSP-кадрами через UDP между двумя процессами.
Команда `Ping` проверяет доступность обработчика, но не меняет Flash или RAM-очередь.
Маяки АСП обязательны: `PayloadSystem<'a, BeaconSocket, ClientSocket, ClientStorage>`
создаётся через `PayloadSystem::new(beacon_socket, client_socket, storage, events,
commands, config)` — ровно шесть обязательных аргументов, два сокета и конфигурация
сразу; состояние `beacon_config` не является `Option`.
Конфигурация создаётся через `BeaconConfig::new(satellite_address, destination)`.
Поля: `satellite_address: Address`, единственное назначение `destination: Endpoint`,
`interval_seconds: NonZeroU16` (по умолчанию `10`). В RX назначение — broadcast
endpoint с CSP-портом `10` на единственном АСП-carrier. Первый маяк отправляется
автоматически через полные 10 секунд работы подсистемы, следующие — каждые 10 секунд.
Отдельного builder для включения маяков и команды отключения нет.
Команда `ConfigureBeacon(config)` перезапускает полный интервал маяка АСП.
Ожидающая отправка маяка не блокирует приём данных и обработку команд.
Уже начатая отправка не отменяется при смене настроек. Если транспорт задержал
отправку дольше периода, пропущенные интервалы не догоняются серией маяков.
Период 10 секунд задаёт расписание, а не гарантированное время выхода в эфир.

`PayloadSystem` также принимает произвольные бинарные datagram на client-порту `11`.
Payload непрозрачен для подсистемы: пустые данные и любые байты допустимы,
декодирования АСП-протокола нет. Три независимых worker обслуживают команды
из внутреннего канала, маяки АСП и приём данных с последовательным `append` в FIFO.
Ожидающий `recv_from` или `append` не блокирует команды и маяки. Отмена всей задачи
во время `append` небезопасна: завершение записи и согласованность счётчиков
при отмене не гарантируются.

`PayloadCommand::SetReceptionEnabled(bool)` управляет только чтением client-данных
через **внутренний канал команд**. `PayloadState.reception_enabled` по умолчанию
равен `true`; `GetState` возвращает текущий режим. Это внутренняя операция ПН,
не команда НС, не отключение радио, CSP Runner или маяков АСП: маяки продолжают
работать с прежним интервалом 10 секунд, `Ping` и остальные команды доступны.
Wire-сообщения `Message` и bridge `serve_commands` не расширены: снаружи остаются
только `Ping` / `Executed`.

Ответ `PayloadEvent::CommandCompleted(PayloadCommand::SetReceptionEnabled(enabled))`
содержит применённый `bool` и формируется сразу после применения режима.
`CommandCompleted(SetReceptionEnabled(false))` означает запрет **новых чтений**,
но не ожидание завершения уже начатого `append`: такая запись завершается ровно
один раз, без отмены или повторного запуска. Ожидающий `recv_from` при переходе
в паузу отменяется; реализация сокета должна обеспечивать cancellation-safe приём.
Пока режим `false`, worker не опрашивает приёмник и не вызывает `discard_oversized`.
Повторная установка того же режима идемпотентна и не отменяет ожидающий приём.
После ошибки приёмника сохраняется backoff 100 мс: pause/resume его не обходит.

Ответы команд не теряются при полном канале событий: ждут свободного места.
Режим меняется только при обработке команды, не при постановке в канал;
новая команда может ждать завершения доставки предыдущего ответа.
Прямой вызов `process_next_command` до `run` позволяет начать работу в паузе:
применённый флаг сохраняется при входе в `run`, а не сбрасывается в `true`.

Пауза **не очищает** удержанные datagram в транспортной очереди. После возобновления
они читаются в FIFO-порядке и получают `received_at_ms` в момент чтения подсистемой
после resume, а не в момент фактического поступления по радио или UDP.
Ограниченная очередь транспорта может отбрасывать новые входящие данные во время
паузы; гарантии доставки и прикладного ACK нет.

RX использует `RamStorage::<MAX_CLIENT_RECORD_SIZE, 16>`: до 16 записей по 272 байта,
без перезаписи старых. `payload::MAX_CLIENT_PAYLOAD_SIZE` равен 256 байтам данных,
`payload::MAX_CLIENT_RECORD_SIZE` — 272 байтам **вместе с 16-байтовым заголовком**.
Это лимиты подсистемы и storage, а не обещание такой же ёмкости транспорта:
в этом примере CSP MTU `255` минус 6 байт CSP-заголовка допускает максимум
249 байт payload без фрагментации. RX печатает максимумы payload/записи и глубину
RAM FIFO при запуске. Фрагментация отложена; CSP и RDP не меняются.

Запись storage кодируется через `payload::client_record_codec::{encode, decode}`;
`HEADER_SIZE` равен `16`. `decode` возвращает
`sat_core::domain::record::ClientRecord { source: Endpoint, received_at_ms: u64, payload: &[u8] }`.
Формат не содержит CSP-заголовка:

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 1 | Версия `1` |
| 1 | 4 | CSP-адрес источника, `u32` big-endian; только допустимые 14-битные значения |
| 5 | 1 | CSP-порт источника, `u8` |
| 6 | 8 | Время чтения подсистемой, `u64` big-endian, монотонные миллисекунды |
| 14 | 2 | Длина payload, `u16` big-endian |
| 16 | 0–256 | Исходные байты payload |

`Address` хранит закрытый `u16` с 14-битным диапазоном `0..=16383`;
`16383` — `Address::BROADCAST`, unicast — `0..=16382`. Адрес создаётся через
проверяемые `Address::new` / `Address::new_unicast`, значение читается через `get()`;
broadcast endpoint — через `Endpoint::broadcast(port)`. Четырёхбайтовое поле
адреса в записи и весь 16-байтовый заголовок сохранены для совместимости:
это не расширяет допустимый диапазон адресов, значения выше `16383` отклоняются.

Записи сохраняются в порядке чтения вместе с исходным endpoint и временем чтения,
не Unix timestamp. `received_datagrams` увеличивается после успешного `recv_from`,
`stored_records` — только после успешного `append`. Отклонённые записи учитываются
в `rejected_records`; ошибки `append`, включая `Full`, также увеличивают
`storage_errors`. Ошибки приёма увеличивают `receive_errors`, затем worker ждёт
100 мс перед повтором. `last_client: Option<Endpoint>` содержит источник последней
успешно сохранённой записи и не меняется при отклонении datagram; начальное значение —
`None`, все пять счётчиков изначально нулевые. Состояние доступно через
`PayloadCommand::GetState` / `PayloadEvent::State`.

Сокет, сохраняющий oversized datagram после ошибки `recv_from`, должен реализовать
синхронный `DatagramSocket::discard_oversized(capacity) -> Option<DatagramMetadata>`.
Метод явно удаляет pending datagram **только при длине больше `capacity`** и возвращает
его источник и полную длину; иначе возвращает `None`, сохраняя pending datagram.
Для транспортов, не удерживающих pending, совместимая реализация по умолчанию
возвращает `None`. После ошибки приёма worker вызывает метод с лимитом `256`:
отброшенный oversized учитывается в `received_datagrams` и `rejected_records`
с событием `ClientRecordRejected(PayloadTooLong)`, но не в `receive_errors`;
затем принимается следующий пакет. При `None` остаются обычная ошибка приёма
и backoff 100 мс. Это локальный контракт сокета, не изменение wire-формата CSP/RDP.

`ClientRecordStored { source, payload_length }` сообщает об успешном сохранении,
`ClientRecordRejected { source, payload_length, reason }` — об отказе:
`ClientRecordRejection::PayloadTooLong` либо `Storage(QueueErrorKind)`, включая
`Full`. Ошибка сокета даёт `ClientReceiveFailed`. Эти уведомления, как и события
маяков, best-effort: полный канал приводит к пропуску события и увеличению
`dropped_notifications`, но не останавливает worker; ответы команд ожидают места
и не отбрасываются. Счётчики отражают операции независимо от доставки уведомлений.

При заполнении FIFO новые записи отклоняются, старые сохраняются. Автоматического
`pop`/`clear`, прикладного ACK на данные и прямой выгрузки/dump на НС в ПН нет.
Командный ответ
`Executed` относится только к `Ping`, не подтверждает сохранение данных АСП.
RAM теряется при остановке или перезапуске RX.

Маяк — `sat_core::protocol::Beacon`; его `encode` / `decode` используют
стандартный `postcard`, без отдельной структуры и ручного формата версии `2`.
Поля: `sat_addr`, `interval_sec`, `timestamp`; здесь `timestamp` — монотонное время
в миллисекундах, не Unix-время. Для приёма используется `Beacon::decode`.
Старый std codec
`csp_demo::Beacon` имеет другой формат и не подходит для этих маяков. Bridge
логирует и пропускает прочие события при ожидании `Pong`, не принимая их за ответ
на команду. Уведомления `BeaconSent { destination }` и
`BeaconSendFailed { destination }` содержат только endpoint назначения.
Одна успешная отправка за интервал увеличивает `transmitted_beacons` на один,
неудачная — `beacon_send_errors` на один. Полный канал событий
не останавливает маяки: обычные уведомления могут пропускаться с увеличением
`dropped_notifications`, ответы команд сохраняются до освобождения места.

Прикладное сообщение занимает 6 байт: версия `1`, тип `1` (`Ping`) или `2`
(`Executed`), затем `u32` request ID в big-endian. CSP-заголовок формирует Runner;
этот codec не меняет формат CSP. Повреждённые сообщения и неизвестные типы
не исполняются. Сетевое представление остаётся в std-примере, не в подсистеме.

UDP не гарантирует доставку. Timeout означает **неизвестный результат**, а не
гарантированный отказ исполнения: запрос или ответ могли потеряться.
Автоматического повтора того же запроса и deduplication нет; request ID нужен
для сопоставления ответов. При перезапуске TX нумерация начинается заново.
Это локальный тестовый канал без аутентификации, не защищённый интерфейс команд.

RX без TX продолжает автоматически отправлять маяк АСП и ждать данные АСП
и запросы тестового bridge. TX можно запустить раньше RX: сетевые ошибки
логируются, единственный RX Runner перезапускается через 250 мс.
Цикл команд TX также продолжает работу после сетевых ошибок. Ошибка первоначального
bind, например занятый UDP-порт, завершает программу.

Проверки:

```sh
cargo test -p examples-std --test payload_commands --features payload --locked --offline
cargo test -p sat-subsystems --lib payload --locked --offline
```

В `payload_commands` теперь 10 тестов; прежние 9 сохранены. Сетевые тесты используют
временные loopback-порты и только пару carrier TX ↔ RX, без интерфейса НС.
Все три теста приёма ограничены общим timeout 5 секунд каждый и не ждут маяков;
тесты полного командного
обмена и маяка АСП сохраняют timeout 15 секунд. Сохранены проверки формата сообщений,
отсутствия ответа до события `Pong`, отклонения некорректных запросов, фильтрации
чужих и запоздавших ответов, timeout без повторной отправки и полного обмена через
настоящие CSP Runner и `PayloadSystem`; уведомление о маяке не заменяет `Pong`.
Тест маяка АСП проверяет отсутствие маяка в первые 9 секунд, получение core `Beacon`
через `Beacon::decode` после 10 секунд, CSP-источник, адрес спутника, единственное
назначение, интервал и монотонный timestamp в миллисекундах, а также исполнение
`Ping` до и после маяка. Проверяются отсутствие второй отправки в том же интервале,
`transmitted_beacons == 1` и отсутствие ошибок отправки.

Тест FIFO передаёт бинарный, пустой и максимальный CSP payload 249 байт через
настоящие CSP Runner и UDP. Обёртка над реальным `RamStorage` копирует записи
для проверки только после успешного `append`, не удерживая `RefCell` borrow
через `.await`. Проверяются источник (два разных CSP-порта), временные границы
и порядок записей, заполнение всех 16 мест и два отказа `Full`. После отказов
тест читает и извлекает исходные записи из настоящего FIFO: старые данные
не изменены и не перезаписаны. `Ping` и `GetState` проверяются непосредственно
через каналы подсистемы, без второго потребителя событий `serve_commands`;
проверяются также счётчики и `last_client` до приёма, при заполнении и после отказов.
Отдельный oversized-тест использует MTU `320`: datagram длиной `257` байт помещается
в CSP, но отклоняется лимитом ПН `256`. Следующий пакет длиной `256` сохраняется;
проверяются событие отказа, счётчики, `last_client`, исходная запись в настоящем FIFO
и содержимое новой записи без потери старых данных.

Десятый тест проверяет pause/resume через прямой канал команд и единственного
потребителя событий, без `serve_commands`. После подтверждённой паузы и проверки
`GetState` с `reception_enabled == false` он отправляет две непрозрачные datagram
через настоящие CSP Runner и UDP в bounded RX-очередь глубиной 2. Короткое окно
тишины 100 мс даёт Runner время поставить пакеты в очередь; сохранений ещё нет,
счётчики остаются нулевыми, `Ping` работает. После подтверждения resume проверяются
два события `ClientRecordStored`, режим `true`, счётчики приёма и сохранения `2`,
отсутствие ошибок и потерянных уведомлений. Через `TracingStorage` и чтение/pop
настоящего `RamStorage` проверяются FIFO, исходные байты и источник, timestamps
не раньше запроса resume и не позже уведомления о сохранении. Тест не ждёт
10-секундного маяка и не меняет его интервал.
