# Правила работы над Rust реализацией CSP

## Задача

Пишем небольшую реализацию CSP v2 на Rust для будущего использования в ПО кубсата. Сначала добиваемся корректного обмена на компьютере с тестовым каналом, затем подключаем Embassy и LoRa.

Основные требования:

- Ядро `no_std`, без обязательной динамической памяти. Host-тесты используют `std` и вызывают то же ядро.
- Простой понятный код важнее скорости и отсутствия копирований.
- Один `Runner` содержит цикл и изменяемое состояние протокола. Приложение запускает его в задаче и пользуется отдельными ручками `Socket` и позже `Connection`.
- Сначала пакеты CSP v2, затем датаграммы, затем RDP. SFP и bitmap ACK появятся отдельными этапами.
- Эталон — конкретная закреплённая версия https://github.com/libcsp/libcsp. Версия формата CSP и версия библиотеки — разные вещи.

Этот комплект заменяет прежние `stages.md` и `profile.md` как задания для агента. Старое большое ТЗ не является обязательной архитектурой: собственные OPEN/READY/DONE и другие предложения из него автоматически не переносить.

## Какие документы читать

- `PLAN.md`: задания и тесты. Выполняй только назначенный этап.
- `STATUS.md`: текущее состояние, решения и следующий шаг. Поддерживай его актуальным.

Прежде чем менять код, прочитай применимые правила репозитория. Если AGENTS.md уже существует, не затирай его; согласованно добавь правила библиотеки или помести этот файл в её подкаталог.

## Когда обязательно советоваться с пользователем

До реализации согласуй:

- устройство Runner и ручек, необходимость отдельного Stack;
- каналы, mutex, waker, `poll_fn`, глобальные static и `unsafe`;
- владение пакетами, если выбор заметно влияет на API;
- обязательную зависимость от Embassy, executor или allocator;
- таймеры RDP и смысл завершения `send`;
- изменения совместимого wire-format и крупную перестройку проекта.

Для согласования достаточно короткого сообщения: задача → два реальных варианта → плюсы и минусы → рекомендация → небольшой пример использования → вопрос. Объясняй влияние на понятность, память, тесты и возможные зависания. Не перечисляй все теоретические варианты.

Дождись ответа на этот выбор; пока можно изучать исходники и делать независимую работу. Уже согласованное повторно не спрашивай. Обычные локальные решения принимай сам.

## Как сохранять простоту

- Не создавать trait, pool, фабрику или отдельную crate без текущей необходимости.
- Копирование небольшого пакета допустимо; zero-copy не цель первых этапов.
- Не делать задачу на каждый слой и универсальный маршрутизатор для одного канала.
- Не добавлять драйверы STM32, LoRa, flash и телеметрию внутрь ядра.
- Не писать вторую реализацию протокола специально для тестов.
- Не переносить C-архитектуру ОС из libcsp; переносить нужные правила пакетов и состояний.
- Не использовать postcard для заголовков совместимого CSP/RDP.
- При ошибочных входных данных и переполнении возвращать ошибку; не обрезать данные и не паниковать.
- Не переписывать unrelated код и не публиковать изменения без задания.

## Как тестировать и отчитываться

Работай маленькими шагами: наблюдаемое поведение → тест → ожидаемое падение → реализация → повторный запуск. Проверяй реальные функции и Runner. Подменяй только среду: канал, время и внешний peer.

Round-trip encode/decode недостаточен: нужны эталонные bytes из libcsp. Если документация и закреплённый код расходятся, покажи это пользователю. При переносе кода соблюдай исходную лицензию.

После этапа выполни host-тесты, форматирование, lint и MCU compile-check. Найди package name и host target сам; не заставляй пользователя заполнять техническую анкету. Если инструмент недоступен, честно отметь непроверенный пункт.

В конце обнови STATUS.md и сообщи: что работает, что реально передано, какие тесты запускались, что осталось и как воспроизвести. Затем остановись до назначения следующего этапа.
