# План реализации CSP v2 на Rust

Это задания для одного агента. Выполнять последовательно: пользователь назначает этап, агент заканчивает его с тестами и останавливается.

## Что строим

Небольшую библиотеку протокола, которую позже можно подключить к STM32F4 + Embassy. Для начала она работает на компьютере через тестовый канал. Ядро с первого дня no_std; тестовая среда — std.

Предлагаемое место — отдельная crate `csp-core` внутри существующего workspace. Агент осматривает проект и предлагает подходящий путь. Пользователю не нужно заранее определять пути, host target и SHA коммита.

Три файла имеют разные роли:

- `AGENTS.md` — постоянные правила и ограничения.
- `PLAN.md` — что реализовать и как проверить.
- `STATUS.md` — что уже сделано и с чего продолжать.

Отдельные profile.md, decisions.md и отчёт после каждого подшага пока не нужны. Небольшие решения и выбранный эталон записываются в STATUS.md. Документация API живёт рядом с кодом.

## Границы первых этапов

| Этап | Результат | Проверяемая передача |
|---|---|---|
| 1 | Корректный формат CSP v2 | Пакет → bytes → тестовая очередь → пакет |
| 2 | Runner и connectionless Socket | Datagram request/reply между двумя узлами |
| 3 | RDP Connection с окном 1 | Несколько коротких сообщений с восстановлением потерь |

Фрагментация SFP будет следующим отдельным этапом. Сначала должны заработать надёжные короткие сообщения. Здесь не реализуются LoRa MAC, маяк, flash, архив, OTA, bitmap ACK и универсальная маршрутизация.

## Текущий согласованный scope

- Этапы 1 и 2 завершены; выполняется этап 3.
- Полный план RDP ниже остаётся ориентиром, но пользователь ограничил первый профиль одним connection и одним подтверждённым DATA.
- Завершены: RDP trailer codec и vectors; handshake; один DATA/ACK; retry SYN/DATA; bounded timeout.
- `send` ждёт ACK. Время поступает явными wrapping millisecond updates без зависимости от executor clock.
- Следующий отдельный подшаг: close/reset и cleanup отмены.
- Несколько сообщений в connection и несколько connection slots отложены на будущее.
- SFP выполняется только после RDP. Wire SFP не смешивается с RDP state machine.
- MAC/window scheduler — отдельный будущий слой после транспорта. Во время этапа 3 не добавляются гарантированные RF RX windows, логика длительного downlink или одновременная организация RX/TX.
- 868 MHz и 435 MHz — два отдельных полудуплексных трансивера. Это ограничение будущей интеграции, но не повод связывать RDP с radio driver.

## Общая проверка после этапа

Агент сам определяет имя package, target компьютера и существующие команды проекта. Требуются:

1. Host unit/integration tests текущей crate.
2. Форматирование и lint без изменения чужого кода.
3. Compile-check библиотеки под target MCU; для обсуждаемого STM32F4 обычно используется `thumbv7em-none-eabihf`, но нужно сверить с проектом.
4. Конкретный тест передачи из текущего этапа.
5. STATUS.md с точными командами и фактическим результатом.

MCU compile-check не является запуском на железе. Отсутствующий C-компилятор или target — непроверенный пункт, а не пройденный тест.

# Этап 1 — Формат пакета CSP v2

## Задание агенту

Создай минимальную библиотеку, которая правильно кодирует и декодирует пакеты CSP v2. Пока без Runner, Socket, соединений и таймеров.

### 1. Подготовка

1. Осмотри workspace и предложи, где создать crate. Если подходящая crate уже есть, не создавай дубль.
2. Предложи стабильную версию libcsp для эталона. После согласования запиши точный commit и путь/ссылку в STATUS.md. Он нужен для воспроизводимости, а не для бюрократии.
3. Найди в этой версии реальные pack/unpack функции заголовка v2, определения полей и флагов. Основной источник: https://github.com/libcsp/libcsp.
4. Кратко опиши поля заголовка, диапазоны, порядок битов и байтов. Сошлись на конкретный файл эталона. Не бери v1-формат из csp-tools.
5. Предложи простое представление пакета. Например, borrowed view для разбора и owned buffer для отправки. Объясни, почему выбранный вариант удобен для следующих очередей Runner, и согласуй до фиксации публичного API.

Не делай fork C-проекта обязательным условием. Достаточно новой Rust crate и отдельного checkout эталона. При переносе кода и fixtures сохраняй необходимые уведомления лицензии.

### 2. Реализация

- `#![no_std]`, без обязательного allocator, без зависимостей от STM32 и executor.
- Минимальные модули: заголовок, packet, ошибки; объединять или разделять по удобству чтения.
- Кодирование в переданный output buffer; разбор header и payload из bytes.
- Явные ошибки недопустимого поля, короткого буфера и превышения MTU.
- Без transmute, сериализации Rust layout и собственной magic-последовательности.
- Payload передаётся без изменений. Граница пакета задаётся тестовым/будущим link, не собственным полем длины внутри CSP header.
- Предложение для стенда: максимум 255 байт целого CSP packet. Это configurable limit, а не обещание окончательного MTU LoRa.
- Начать с пакетов без optional CRC. Поддержка CRC не обязательна для завершения этого этапа; если добавляется, отдельным подшагом сверить coverage и trailer по эталону.
- Неподдерживаемые флаги не игнорировать так, чтобы служебные bytes выдавались за обычный payload. Согласовать ограничение профиля; зарезервированные биты обрабатывать по проверенным правилам upstream.

Не добавляй заранее незадействованные Connection, router, pool и набор generic traits.

### 3. Тесты до завершения

| Проверка | Ожидаемый результат |
|---|---|
| Несколько известных headers | Bytes побайтно совпадают с независимым эталоном libcsp |
| Минимум/максимум каждого поля | Допустимые значения сохраняются; недопустимые не обрезаются |
| Поля source/destination и порты различаются | Их нельзя незаметно перепутать |
| Input короче header | Ошибка без panic |
| Output на байт короче нужного | Ошибка без выхода за пределы |
| Пустой payload и payload до предела MTU | Разбор сохраняет весь payload |
| Payload выше лимита | Ошибка, а не усечение |
| Encode → decode | Дополнительная проверка, не замена эталонным bytes |

Если CSP header не содержит длину payload, decoder без внешней информации/CRC не обязан определять его усечение. Не придумывай невозможную проверку.

### 4. Итоговая передача

Напиши integration test `packet_over_memory_pipe`:

1. Создать packet с известными полями и payload.
2. Закодировать production encoder.
3. Передать bytes через маленькую очередь в памяти.
4. На другой стороне разобрать production decoder.
5. Проверить все поля и payload.
6. Сравнить отправленные bytes с fixture libcsp.

Для fixtures нужен независимый источник: минимальная C-утилита, вызывающая реальные функции выбранного libcsp, или существующий воспроизводимый upstream-тест. Не писать второй самодельный encoder и не считать его эталоном. Запиши способ генерации и commit. Если C нельзя собрать, честно отметь, какие сравнения ещё не выполнены.

### Результат этапа

Рабочий codec, тест передачи bytes, независимые vectors и короткий пример использования. Это ещё не сеть и не Runner. Обновить STATUS.md, показать команды проверки и остановиться.

# Этап 2 — Runner и ненадёжные датаграммы

## Задание агенту

Используя codec этапа 1, сделай два узла, обменивающихся однокадровыми сообщениями без подтверждений. Цикл обработки должен жить в Runner, приложение должно пользоваться Socket.

### 1. Сначала согласовать устройство

До реализации объясни:

- кто создаёт и владеет Runner, Socket и их ресурсами;
- нужен ли отдельный Stack или достаточно конструктора и Socket;
- как Socket передаёт запрос и будит Runner;
- как входящий packet попадает в правильный Socket;
- как runner обслуживает RX и TX, пока клиент ожидает;
- что происходит при заполнении очередей;
- каким способом запускать Runner в host-тесте.

Сравни два реальных варианта общения ручек с Runner. Например, bounded channels и shared state с уведомлением. Для каждого опиши понятность, владение, ограничения памяти, риск зависаний и зависимости. Предложи один вариант и дождись согласования.

Если нужны embassy-sync, mutex, poll_fn или свои waker, объясни необходимость. Не заставляй core зависеть от конкретного executor без согласования. Host executor может быть dev-only.

Требование — работающий async Runner; это не требование писать всю внутреннюю логику через async. Codec и обычные переходы состояния остаются синхронными.

### 2. Реализация

1. Runner владеет изменяемым состоянием и выполняет цикл только когда приложение его запускает/опрашивает.
2. Приложение само запускает Runner в concurrent future или задаче. Библиотека не создаёт потоки и не вызывает executor изнутри.
3. Socket привязывается к локальному порту и позволяет `send_to`/`recv_from` либо эквивалентные согласованные операции.
4. Получатель видит source address и source port, чтобы ответить.
5. Все исходящие данные проходят через codec и packet link; все входящие — обратно через реальный Runner.
6. Datagram не создаёт handshake, ACK, retry и connection state.
7. Чужой destination не доставляется локально и не пересылается дальше. Универсальный router не нужен.
8. Реализуй один packet link на узел и два локальных порта в тестах. Не разрабатывай все служебные сервисы libcsp.
9. Очереди ограничены. При переполнении — согласованный Busy/ошибка/ожидание; без бесконечного взаимного ожидания.
10. Явно объясни, когда завершается send: запрос принят локально или packet отправлен link. Удалённая доставка не гарантируется.

Отдельно согласуй минимальный link API. Один link должен уметь отправлять и принимать; он не обязан физически делать оба действия одновременно. Не проектируй API, которое заведомо невозможно реализовать для полудуплексного модема, но сам LoRa MAC пока не пиши.

### 3. Тестовый канал

Сделай маленький FakeLink: две очереди serialized packets между узлами. В host-тестах допустимы std VecDeque и Vec.

Достаточно уметь передать, потерять следующий packet, дублировать его и удержать до команды теста. Mock-фреймворк и подробная RF-модель не нужны.

### 4. Тесты до завершения

| Проверка | Ожидаемый результат |
|---|---|
| Packet на открытый порт | Целый payload и правильный source у Socket |
| Другой destination | Нет локальной доставки |
| Неоткрытый порт | Определённая обработка без зависания |
| Разные локальные порты | Доставка нужному Socket |
| Payload выше MTU | Ошибка до отправки |
| Повреждённый header | Нет app delivery, Runner продолжает работать |
| Заполненная TX-очередь | Нет deadlock; RX продолжает обслуживаться |
| Заполненная RX-очередь приложения | Согласованная политика без бесконечного ожидания |
| Packet потерян | Нет автоматической повторной передачи |
| Packet продублирован | Дубликат допустим; datagram не получает скрытой надёжности |

### 5. Итоговая передача

Integration test `datagram_request_reply`:

1. Создать узлы A и B с независимыми Runner и Socket.
2. Запустить оба Runner вместе с приложениями.
3. A отправляет `hello`, B получает его и отвечает `world` по source metadata.
4. Проверить bytes, адреса, порты и число передач.
5. Повторить с потерей request или reply: приложение не получает ответ, а транспорт не делает retry. Тест заканчивается ограниченным способом, не висит.
6. Проверить конкурентную отправку datagrams в обе стороны, без обещания проверки RF-полудуплекса.

Для async-тестов нужен безопасный способ остановить/отменить бесконечный runner future. Согласуй простой вариант; отдельный сложный shutdown-протокол ради теста не нужен.

Дополнительно организуй один smoke test Rust ↔ libcsp для datagram через простой host carrier или reference harness. Не включай C-зависимость в firmware crate. Если это не удалось выполнить, обозначь непроверенную совместимость, а не заменяй её Rust ↔ Rust тестом.

### Результат этапа

Datagram API через Runner и Socket, рабочий request/reply, проверка потерь и переполнения. Нет RDP, SFP и радио. Обновить STATUS.md и остановиться.

# Этап 3 — RDP соединение с окном 1

## Задание агенту

Добавь надёжное соединение по правилам закреплённого libcsp. Используй окно 1, чтобы сначала проверить поведение без сложного управления несколькими неподтверждёнными пакетами. Несколько коротких сообщений передаются в одном Connection.

Этап выполняется по подшагам: источник и решения → handshake → DATA/ACK → повторы и закрытие. Не генерировать весь автомат одним большим изменением.

### 1. Изучить и согласовать

Найди в закреплённом libcsp RDP header, установление, номера пакетов, ACK, timeout, reset и закрытие. Схематично объясни необходимые состояния и служебные пакеты. API C не обязательно повторять на Rust; wire-поведение должно соответствовать эталону.

До реализации согласуй:

- API `connect`, приёма соединения и Connection;
- смысл завершения send: локальная очередь, ACK или отдельный ticket;
- источник монотонного времени и управление им в тестах;
- начало timeout, если packet ещё ждёт link send;
- очистку при timeout, close и отмене операции.

Предложи простой способ управляемого времени. Он не обязан быть generic Clock trait; явные timestamps могут быть проще. Не использовать реальный sleep для timeout-тестов.

Проверь по исходникам допустимость окна 1 и возможность выключить delayed ACK. Если эталон требует другой минимальный профиль, объясни это и согласуй. Не изобретай несовместимый stop-and-wait с похожими названиями пакетов.

### 2. Установление

1. Добавь RDP codec с independent vectors.
2. A инициирует connection, B слушает/принимает.
3. В тестовом профиле допустимо одно активное connection на узел; одновременное открытие не входит.
4. Handshake проходит через тот же Runner и packet link, что datagrams.
5. Повтор handshake не создаёт второй app connection.
6. Недоступный peer приводит к конечной ошибке; слот освобождается.

Сначала добейся тестов handshake, затем добавляй DATA.

### 3. Сообщения, ACK и повторы

1. Отправляй один DATA, ожидай корректный ACK.
2. Храни bytes неподтверждённого сообщения до ACK или ошибки.
3. При потере DATA выполняй повтор по правилам RDP.
4. При потере ACK receiver повторяет нужное подтверждение, но не отдаёт сообщение приложению второй раз в живом connection.
5. Несколько send используют то же connection и продолжающуюся транспортную нумерацию.
6. Короткий reliable reply передаётся обратно в том же connection. Для первого теста достаточно последовательного request/reply.
7. Datagram Socket продолжает работать, пока RDP ждёт ACK; весь Runner не блокируется.
8. Проверяй peer, порты и допустимость sequence/ACK. Старый ACK не должен подтверждать новые данные.
9. Переполнение sequence проверяй по реальным правилам RDP, а не обычным сравнением чисел.

Своих OPEN/READY/DONE, bitmap и дополнительных wire session_id здесь нет. При необходимости изменения совместимости сначала обсудить его с пользователем.

### 4. Завершение

- Реализуй нужное закрытие/reset по выбранному upstream.
- Не объявляй успех неподтверждённым сообщениям при close.
- После timeout освободи ресурсы, чтобы можно было установить новое connection.
- Опиши неизвестный исход: sender без ACK не может утверждать, что receiver ничего не получил.
- Согласуй простую отмену ожидающего клиента. Она не должна оставлять вечно занятый слот.
- Не обещай exactly-once после перезапуска и окончания жизненного цикла connection.

### 5. Тесты до завершения

| Проверка | Ожидаемый результат |
|---|---|
| RDP codec | Совпадение с C-эталоном |
| Обычный handshake | Одно connection у каждой стороны |
| Потеря каждого служебного handshake packet | Восстановление или ожидаемый bounded отказ по выбранным правилам |
| Peer отсутствует | Timeout и возврат ресурсов |
| Потерян DATA | Повтор и одна app delivery |
| Потерян ACK | Повтор DATA без повторной app delivery |
| Дублирован DATA/ACK | Корректное состояние, нет лишней доставки |
| Три сообщения в одном connection | Порядок и границы сохранены |
| ACK другого peer/порта | Не подтверждает сообщение |
| Постоянный обрыв | Конечная ошибка без утечки ресурсов |
| Sequence wraparound | Правильная работа на границе счётчика |
| Close → новое connection | Повторное использование одного доступного слота |
| Datagram во время ожидания ACK | Runner продолжает его обслуживать |
| Прикладной RX заполнен | Поведение по проверенной flow-control модели RDP; принятые данные не теряются молча |
| Клиент отменил ожидание | Определённая очистка, без зависания |

### 6. Итоговая передача

Integration test `rdp_messages_with_loss`:

1. A и B запускают настоящие Runner через FakeLink.
2. A устанавливает connection к пользовательскому порту B.
3. A посылает `one`, `two`, `three` как отдельные короткие сообщения.
4. Канал теряет первый DATA второго сообщения и первый соответствующий ACK третьего.
5. Тест продвигает виртуальное время. Выбор теряемых packets делается по их реальным RDP-полям, не случайному порядковому номеру в логе.
6. B получает ровно три сообщения в правильном порядке.
7. B передаёт reliable reply по тому же connection, A получает его.
8. Connection закрывается, ресурсы доступны снова.
9. Другой вариант с полной потерей линии завершается ошибкой за конечное виртуальное время.

Расширяй FakeLink только нужными функциями. Не делай отдельный протокол в тестовом harness. Добавь проверку Rust ↔ закреплённый libcsp для handshake и коротких reliable messages через один согласованный host carrier.

### Результат этапа

Целевой полный результат: RDP-профиль для connection с окном 1, тест потерь, reference comparison и сохранённый datagram API. Первый утверждённый профиль ограничен одним connection и одним подтверждённым DATA; дальнейшие сообщения, несколько slots и close выполняются отдельными подшагами. Нет SFP и больших блоков.

- [Основы CSP](https://libcsp.github.io/libcsp/basic.html) — обзор; детали сверять с закреплённым commit.
- [CSP API](https://libcsp.github.io/libcsp/api/csp_h.html) — термины connectionless, Socket и Connection.
- [RDP source](https://github.com/libcsp/libcsp/blob/48f7fb0b57f610bf65bab1aa2d1357c3b9722782/src/csp_rdp.c) — точный закреплённый RDP wire format и state machine.
- [RDP connection fields](https://github.com/libcsp/libcsp/blob/48f7fb0b57f610bf65bab1aa2d1357c3b9722782/src/csp_conn.h) — состояния и sequence fields.
- [Router integration](https://github.com/libcsp/libcsp/blob/48f7fb0b57f610bf65bab1aa2d1357c3b9722782/src/csp_route.c) — создание/поиск connection и передача RDP packet в transport.
- [Rust wrapper libcsp](https://docs.rs/libcsp/latest/libcsp/) — необязательный инструмент reference peer, не собственная Rust-реализация транспорта.
- [csp-tools](https://github.com/daniestevez/csp-tools) — host tools; published codec v1 не использовать как эталон заголовка v2.
